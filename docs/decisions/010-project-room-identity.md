# ADR-010: Room は Project、識別は clientId と表示名

- ステータス: 採択（設計判断）。実装は未了
- 日付: 2026-10-26
- 関連: GitHub issue #21（親エピック #2）
- 前提: [ADR-008](./008-local-server.md)、[ADR-009](./009-command-event-sync.md)

この文書は、[implementation-plan.md](../implementation-plan.md) §0 と §1.3 の Room と利用者識別を記録する。接続実験や脅威分析の結果は入力にない。計画にないトークン形式、フラグ名、認証方式は、ここでは決めない。

## 文脈

concept.md §1.5 は、初期版で多人数のリアルタイム編集と、複雑な権限管理をしない、と書いている。§10.2 は、将来の共同利用では認証・認可・監査ログ・研究契約上の共有制限を実装する、と書いている。§11 の M4 は、研究室内共有、権限管理、バックアップと監査を将来に置いている。§15 は Collaboration を M4 としている。§13.1 の実装指示は、認証機能を先行実装しない、と書いている。

implementation-plan.md §0 は、共同編集を「Room（= Project）単位のリアルタイム同期」に改める。権限管理と本格認証は、引き続き M4 である。この行の理由は「discussion room」用途である、とだけ書かれている。§3 は「M4（研究室データ基盤連携・権限管理など）は issue 化しない」とする。

データモデルでは、Project の下に複数の Board があり、Artifact は Project に属し、複数 Board の CanvasItem から参照される（concept.md §7.1、§7.2。分離そのものは ADR-002）。計画 §1.3 は、この形を配信単位の理由にしている。

利用者識別について、計画 §1.3 は `clientId`（localStorage）と表示名と書き、本格認証は M4 としている。§1.2 の `hello` は `protocolVersion`、`clientId`、`displayName`、任意の `token` を持つ。

## 決定

1. **Room = Project** とする。一つの Project が一つの Room であり、配信の単位は Project である。Artifact が Project スコープで複数の Board から参照されるため、Project 単位で配信すれば整合を取りやすい、という計画 §1.3 の理由を採用する。クライアントは、表示中でない Board の CanvasItem の event を状態には反映し、描画はしない。
2. 利用者の識別は `clientId` と表示名とする。`clientId` の置き場所は localStorage である（計画 §1.3）。これは接続しているクライアントの識別であり、認証ではない。表示名が本人であることを確認する手順は、計画にない。
3. 本格認証、権限管理、研究室データ基盤との連携は M4 のままとする。計画 §3 のとおり、M4 は issue 化しない。この ADR は認証方式を設計しない。
4. サーバーの待受の既定は `127.0.0.1` とする。LAN へ公開するときは、明示的なフラグと Room トークンの両方を必須とする（計画 §1.3）。`hello` の `token` は §1.2 では任意として描かれている。LAN 公開時にトークンが必須であることと、この任意表記をどう契約に書くかは、後続のプロトコル作業（計画の E3）に残す。トークンの形式、保管、有効期限、フラグの名前と設定方法は計画にないため、ここでは決めない。
5. 参加中のメンバーを知らせるメッセージとして、計画 §1.2 は `joined` の `members[]` と、`member`（`joined` または `left`）を描いている。メンバーオブジェクトのフィールドは、この概略以上には書かれていない。ここではフィールドを追加しない。

Room への接続、localStorage への `clientId` の保存、待受アドレス、LAN のフラグ、トークンの検証は、この文書では実装しない。

## 代替案

1. **初期版ではリアルタイムの共同編集をしない（concept.md §1.5）**  
   計画 §0 は、discussion room として使うために、Room 単位の同期を採る。同じ行で、権限管理と本格認証は M4 に残す。§1.5 のうち複雑な権限管理を初期に持たないことは維持される。多人数のリアルタイム編集をしない、という部分は、計画 §0 が置き換える。

2. **Board ごとの Room**  
   計画 §1.3 は、Artifact が複数 Board から参照されることを理由に、配信単位を Project としている。Board ごとに Room を分けた場合に整合をどう取るかは、計画に手順がない。Board 単位と Project 単位を試作して比べた記録もない。

3. **初期から認証と認可を実装する**  
   concept.md §10.2、§11 の M4、§13.1、§15、および計画 §0 と §3 は、本格認証と権限管理を M4 に残し、いまは issue にしない。アカウント方式の比較は、これらの文書にない。

4. **既定の待受を LAN や全インタフェースにする**  
   計画 §1.3 は既定を `127.0.0.1` とし、LAN 公開を、明示フラグと Room トークンが両方ある場合に限る。concept.md §10.2 は、明示的な操作がない限り研究データを外部へ送らない、と書いている。待受を最初から広げる根拠は、計画にない。

## 結果

- 同じ Project を開いたクライアントは、一つの Room に入る。表示する Board を変えても Room は変わらない。表示していない Board の CanvasItem の event も、クライアントの状態には入る。計画 §1.3 が省くのは描画であり、状態を持たない最適化は計画に書かれていない。
- Event の `actor` が指せる主体は、認証された利用者ではない。計画上、接続の識別は `clientId` と表示名である（ADR-009 は `actor` のフィールド対応をここでは作らない、と記録している）。なりすましを防ぐ方式は、M4 より前の文書にはない。
- 既定の待受は `127.0.0.1` である。ほかのマシンから接続できる状態にする操作は、明示フラグと Room トークンがそろった LAN 公開に限る。トークン検証に失敗したときのメッセージは、計画 §1.2 にない（`reject` は command 向けとして描かれている）。
- 本格的な認可、研究契約上の共有制限、研究室データ基盤との接続は M4 に残る。一方、変更履歴の「誰が・なぜ・何を」（concept.md §7.6）と、implementation-plan.md §1 の event log および Event の `actor` / `commandId` は同期方式の判断に含まれる。これらを M4 の本格的な認証・監査と同一視しない。§7.6 の「誰が・なぜ・何を」について、M4 より前に記録できる「誰が」は、`clientId` と表示名の範囲である。
- 計画 §3.2 の M0「二つのブラウザで同じ Room に入る」は、この文書の採択だけでは満たさない。
