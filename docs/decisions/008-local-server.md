# ADR-008: ローカルサーバー + ブラウザ、永続化は SQLite + ファイルシステム

- ステータス: 採択（設計判断）。実装は未了
- 日付: 2026-10-26
- 関連: GitHub issue #21（親エピック #2）
- 置き換える判断: [concept.md](../concept.md) §17 ADR-001（ローカルファースト SPA）

この文書は、[implementation-plan.md](../implementation-plan.md) の「0. 前提の改訂」に書かれた実行形態と永続化を記録する。計測、試作、性能比較の結果は入力にない。計画にない製品選定や手順は、ここでは決めない。

## 文脈

concept.md は、サーバー不要・ローカル保存・単独ユーザー・ブラウザ完結の MVP から始める（§0）。設計原則 Local first は「AI 接続・サーバーがなくても中核機能が使える」ことである（§1.4）。初期版では多人数のリアルタイム編集と複雑な権限管理をしない（§1.5）。永続化は IndexedDB（Dexie 等）と OPFS（対応できない場合は IndexedDB の Blob）である（§7.4、§8.1、§8.2）。

ADR-001 は、そのローカルファースト SPA を、機密性・初期運用コスト・配布容易性を理由に採っている。再検討条件は「多人数共有が必須になったとき」である（§17）。共有用のバックエンドは、将来の拡張として「Hono + SQLite / MongoDB 等」とだけ書かれている（§8.2）。研究室データ基盤としての MongoDB 等は M4 にある（§11）。

implementation-plan.md は、concept.md と食い違う箇所では「0. 前提の改訂」を優先すると定めている。実行形態は、手元の PC で起動するローカルサーバー + ブラウザに改める。理由は、WebSocket Room による同時閲覧・議論を可能にするためである。永続化は、サーバー側の SQLite + ファイルシステム（blob）に改める。理由は、複数クライアントに対する単一の正（source of truth）が必要なためである（§0）。§1 の構成図では、ブラウザが WebSocket と HTTP でそのサーバーに接続し、サーバーが SQLite と `dataDir/blobs/<sha256>` を持つ。§1.4 はサーバーを Node + Hono + WebSocket + SQLite として置いている。

Room の単位と利用者の識別は [ADR-010](./010-project-room-identity.md)、更新の通り方は [ADR-009](./009-command-event-sync.md) が記録する。

## 決定

1. 実行形態は、研究者が手元の PC で起動するローカルサーバーと、それに接続するブラウザとする。計画 §1 と §1.4 はそのサーバーを、Node 上の Hono（HTTP と WebSocket）として描いている。ほかの HTTP ライブラリとの比較は計画にない。
2. 複数クライアントが共有する正は、サーバー上の SQLite と、ファイルシステム上の blob とする。計画の構成図は blob の位置を `dataDir/blobs/<sha256>` と書いている。このパス表記は構成のスケッチであり、設定キーの確定ではない。
3. concept.md ADR-001 を、この決定が置き換える。IndexedDB（Dexie）と OPFS を永続化の正とする §7.4 と §8.2、および同前提の §8.1・§8.3・§15 の記述も同様に置き換える。§11 M0 の IndexedDB による保存・復元の項目を含め、完了条件は implementation-plan.md §3.2 を優先する。
4. 本 ADR の採択は、SQLite、blob 保存、WebSocket、ブラウザからの同期が実装されたことを意味しない。それらの課題は計画の E4（ローカルサーバー）ほか後続のエピックに残っている（§3）。M0 の「主要 ADR が揃っている」は文書の条件であり、同じ M0 にある二ブラウザでの同期は別の完了条件である（§3.2）。

## 代替案

計画または concept.md に名前があるものだけを挙げる。

1. **ADR-001 のまま（サーバー不要の SPA。IndexedDB + OPFS）**  
   concept.md の初期方針である。計画 §0 は、WebSocket Room で同時に閲覧・議論するには手元のローカルサーバーが必要であり、複数クライアントの単一の正にはサーバー側の保存が必要だとして、この案を採らない。

2. **共有用バックエンドは将来まで持たない（concept.md §8.2 の Future Backend、§1.5）**  
   concept.md は Hono + SQLite / MongoDB 等を、共有機能の将来拡張としている。計画は discussion room のためにローカルサーバーとリアルタイム同期を前に出し、権限管理と本格認証は M4 のままにしている（§0、§3）。MongoDB 等は concept.md の M4（研究室データ基盤）に残り、計画は M4 を issue 化しない。ローカルの正として MongoDB を選んだ記録は計画にない。

3. **サーバーで任意の Python を実行する**  
   計画 §0 は Pyodide + Web Worker を変更しない。実行はクライアントが行い、結果をサーバーに保存して Room に共有する。理由は、サーバーで任意コードを実行しないためである。

## 結果

- 共有される状態の読み書きは、手元でローカルサーバーが動いていることを前提に、サーバー経由で行う。ブラウザ単体の IndexedDB / OPFS を、その正にはしない。UI 状態と楽観的更新の置き場所は、計画 §1 の図が Zustand と書いている。IndexedDB をキャッシュとして残すかどうかは計画にないため、ここでは決めない。
- concept.md §1.4 の「サーバーがなくても中核機能が使える」、§10.1 の Offline、§0 の「サーバー不要」は、この決定と食い違う。食い違う箇所は implementation-plan.md の「0. 前提の改訂」を優先する。オフラインのときにどの操作を許すかは、計画に手順がないため、ここでは決めない。
- 運用ではサーバープロセスを起動する。ADR-001 が理由に挙げていた「サーバー不要であることによる配布の容易さ」は、この決定の理由には残らない。待受アドレスと LAN 公開の条件は ADR-010 が記録する。
- UI から SQLite や Pyodide を直接触らない、という計画 §4 の境界は維持する。Python の実行場所はクライアントのままである（計画 §0）。
- blob の識別に sha256 を使う点は、concept.md §7.4（同一ファイルの重複判定）および §7.2 の `DataBlob.sha256` と、計画のパス表記が同じ識別子を指している、と読める。ZIP エクスポート（concept.md §7.5。計画の E8 と M1 の round-trip）の成否は、本 ADR では扱わない。
- SQLite のテーブル、マイグレーション、トランザクション境界の詳細は、計画 §1 の「Valibot 検証 → domain の純粋関数 → SQLite トランザクション → event log」以上には書かれていない。それらをこの ADR では埋めない。適用の順序は ADR-009 が記録する。
- 計画 §0 は、AI 接続についても「最初からサーバー側 AiProvider。API キーはサーバーの環境変数のみ」と改訂している。理由は、キーをフロントに置かないためである。これは concept.md §6.5（秘密鍵を配布済みフロントにハードコードしない。共有・本番運用ではサーバー側プロキシが必要）と同じ方向で、時期を前に出した行である。AiProvider の実装は計画上 M3 / E13 であり、本 ADR はアダプターの中身を決めない。concept.md §6.5 の「MVP では AI なしで全基本機能が動く」は、計画 §0 が踏襲すると書いた科学的制約や AI 差分承認と別に、この行との関係が計画本文では分解されていない。ここではその関係を新しく定義しない。
- 計画 §0 が concept.md をそのまま踏襲すると書いたもの（Artifact と CanvasItem の分離、3 種の線、DAG、AI 差分承認、Provenance、科学的制約）は、この決定では変更しない。
