# ADR-009: サーバー権威の Command / Event 同期

- ステータス: 採択（設計判断）。実装は未了
- 日付: 2026-10-26
- 関連: GitHub issue #21（親エピック #2）
- 前提: [ADR-008](./008-local-server.md)（共有される正はローカルサーバーの SQLite）。Room の範囲は [ADR-010](./010-project-room-identity.md)

この文書は、[implementation-plan.md](../implementation-plan.md) §1.1 と §1.2 の同期方式を記録する。計測、試作、CRDT 実装との比較実験は入力にない。計画が書いていない閾値、フィールド一覧、メッセージの厳密なスキーマは、ここでは作らない。

## 文脈

複数のクライアントが同一の Project を同時に閲覧・編集する（implementation-plan.md §0）。その正はサーバーに置く（ADR-008）。

concept.md は、科学的な結論に関する重要変更について「誰が・なぜ・何を」を記録する（§7.6）。AI が作った変更は、研究者が差分を承認するまで保存しない（§6.3、§17 ADR-006）。拒否した AI 提案は DB に反映しない（§12.2。計画 §3.2 の M3 完了条件は「承認しない提案は DB に一切反映されない」）。外部入力は Valibot で検証し、ドメインの適用は純粋関数で行う（concept.md §8.5、計画 §4）。

計画 §1.1 は、同期をサーバー権威の Command / Event とし、CRDT（Yjs）は採用しない、と書いている。再検討は「テキスト同時編集の要求が強くなったら」行い、そのときは ADR にする、とも書いている。本 ADR は現在の不採用判断と再検討条件を記録する。再検討そのものは将来の別 ADR で行う。

## 決定

クライアントは Command を送る。サーバーは次の順で扱う（計画 §1.1 と §1 の構成図）。

1. Valibot で検証する。
2. `packages/domain` の純粋関数で適用する。
3. SQLite のトランザクションで保存する。
4. `seq` 付きの Event を、その Room の参加者へ broadcast する。

クライアントは Command を楽観的に適用し、`reject` を受けたらロールバックする。

各エンティティは `version` を持つ。

- 位置とサイズは LWW とする。
- 本文などの内容更新は、`baseVersion` が一致しないとき、フィールド単位でマージできるかを判定する。できない場合は reject する。
- テキストは、編集中のソフトロック（Presence）で衝突を避ける。

再接続時は、`lastSeq` より後の event を再送する。計画が「古すぎる」とする場合は、スナップショットを渡す。

メッセージの概略は計画 §1.2 のとおりとする。

- C→S: `hello`、`join`、`command`、`presence`、`ping` / `pong`
- S→C: `joined`、`ack`、`reject`、`event`、`member`、`presence`、`ping` / `pong`

`presence` は永続化せず、間引く。`hello` の項目（`protocolVersion`、`clientId`、`displayName`、`token?`）の意味のうち、識別とトークンの位置づけは ADR-010 が記録する。

CRDT（Yjs）は採用しない。理由と、再び比較する条件は次節のとおりである。

この採択は、`packages/protocol` のスキーマ、domain の適用関数、サーバーのパイプラインが実装されたことを意味しない。それらは計画の E2（Command 適用の純粋関数）、E3（メッセージ契約、resume、競合方針）、E4（Command パイプライン）に残っている（§3）。

## CRDT（Yjs）を採用しない理由

計画 §1.1 は、CRDT（Yjs）を採用せず、次とサーバー権威モデルとの相性を優先する、と書いている。性能や同時編集の成功率の測定値は、計画にも concept.md にもない。

- 監査ログ（誰が・なぜ・何を）。問いの形は concept.md §7.6 と同じである。
- 境界での検証。サーバーは Valibot で検証してから保存する。
- AI 提案の承認フロー。未承認の提案は保存しない（concept.md ADR-006、§6.3。計画の M3 は「承認しない提案は DB に一切反映されない」）。

## 再検討条件

計画 §1.1 は「テキスト同時編集の要求が強くなったら再検討（ADR化）」と書いている。本 ADR は現在の不採用判断と再検討条件を記録する。再検討そのものは将来の別 ADR で行う。

「強くなった」を判定する人数、遅延、競合率などの閾値は、計画にない。この ADR では閾値を新設しない。位置・サイズの LWW や ADR-006（AI 差分承認）を、この一文だけで変更するとは計画は書いていない。それらを変えるかどうかは、再検討の ADR が扱う。

## 代替案

1. **CRDT（Yjs）**  
   計画 §1.1 が名前を挙げ、採用しないとした方式。理由と再検討条件は前節のとおりである。Yjs 以外の CRDT ライブラリの比較は計画にない。

2. **各クライアントが IndexedDB を正として書く（ADR-001 の保存の延長）**  
   複数クライアントに対して単一の正をサーバーに置く ADR-008 と両立しない。AI 提案の承認制約自体は保存場所に依存せず、元の IndexedDB 設計でも満たすべき要件である。計画 §0 はこの延長を、共有される正としては採らない。

計画 §1.1 は、全フィールドを一つの規則にまとめてはいない。位置・サイズ、内容、テキストで方針を分けている。操作変換など、文書に名前がない方式の採否は記録されていない。

## 結果

- 正として保存され、Room に broadcast されるのは、サーバーが検証して適用した Command に対応する Event である。`reject` はその Command について正を進めない。楽観的に適用したクライアントは、その更新を戻す。
- 再接続後の追いつきは、`lastSeq` 以降の event の再送か、スナップショットである。`seq` の一意範囲（Room ごと、プロセスごと、など）は、メッセージが `projectId` と `seq` を一緒に持つこと以上には計画が定義していない。メッセージ契約は E3 の成果として計画にある。この ADR では採番の範囲を決めない。
- 「古すぎる」の閾値と、スナップショットの中身は、計画にない。
- `baseVersion` が一致しないときの「フィールド単位のマージ可否」について、対象フィールドの一覧は計画にない。判定は後続の domain の純粋関数で定義する。この ADR では一覧を作らない。
- Presence（計画 §1.2 の `boardId`、`cursor?`、`selection[]`、`editingItemId?`）は正のデータではない。永続化せず、間引く。監査の「誰が・なぜ・何を」は、計画が CRDT を採らない理由として挙げ、Event は `actor` と `commandId` を持つ。その `actor` と ADR-010 の識別子とのフィールド対応は、§1.2 の概略より細かくは書かれていない。ここでは対応表を作らない。
- HTTP / WebSocket のハンドラに domain ロジックを書かない（計画 §4）。適用は `packages/domain` の純粋関数に置く。
- 計画 §3.2 の M0「二つのブラウザで同じ Room に入り、Markdown カードの移動が同期される」は、この文書の採択だけでは満たさない。
